Worked examples and reference protocol
============================================

.. index:: example, checkout

A minimal handle transformation
-------------------------------------

.. weave-check:: ../../examples/valid/arm_hold.weave
   :expect: ACCEPT
   :profile: F0/N0

The helper accepts ownership of one Hold and returns one Escrow with unchanged
indices. The issuing transition also creates registration state. The declaration
of that transition belongs to the net, not the helper.

Handling all outcomes
---------------------------

.. weave-check:: ../../examples/valid/settle.weave
   :expect: ACCEPT
   :profile: F0/N0

Each branch receives a different nominal resource. Selling Unpaid or releasing
Paid is a type error even when identities match. Unknown explicitly moves to
recovery. No branch is allowed to silently return with its payload still live.

Composition with propagation
----------------------------------

.. weave-check:: ../../examples/valid/checkout_propagating.weave
   :expect: ACCEPT
   :profile: F0/N0
   :linenos:

The first helper handles all results returned by place_order. The second changes
the success payload from Paid to Unit by selling. The third arms the hold and
propagates payment outcomes. Err and Unknown preserve their payload obligations
through both helper boundaries.

The exact checked expansion is generated by ``scripts/validate.py`` into
``validation/lowered-checkout.weave``. It can be checked independently with the
same net and is not a compiler binary.

An invalid normal return
------------------------------

.. weave-check:: ../../examples/invalid/drop_hold.weave
   :expect: E204
   :profile: F0/N0

Expected rejection: E204. The existence of cancel_held does not permit an
ordinary return to abandon Hold.

An invalid propagation boundary
-------------------------------------

.. weave-check:: ../../examples/invalid/early_return_leak.weave
   :expect: E204
   :profile: F0/N0

Expected rejection: E204. An obligation consumed only after successful
propagation remains live on Err/Unknown exits. Version 3 identifies the
propagation source line and outstanding handle.

Invalid identity substitution
-----------------------------------

.. weave-check:: ../../examples/invalid/wrong_order.weave
   :expect: E209
   :profile: F0/N0

Expected rejection: E209. A resource belonging to one symbolic order cannot
authorize a request for another. The checker compares symbolic identities; it
does not assume that two scalar parameters happen to be equal.

Observed legacy execution
-------------------------------

The validation script runs the complete checkout with each scripted outcome.

.. list-table::
   :header-rows: 1

   * - Outcome
     - Available
     - Sold
     - Recovery queue
     - Registration
   * - Ok
     - 0
     - 1
     - 0
     - 0
   * - Err
     - 1
     - 0
     - 0
     - 0
   * - Unknown
     - 0
     - 0
     - 1
     - 1

This table concerns Inventory N0 and its in-memory, one-order simulator only.
Inventory N1 is a different protocol; see :doc:`protocol-diff`. It deliberately preserves
Unknown's recovery obligation. The legacy simulator may retain its adapter
request token. It does not model the N1 worker pool or R0 durable completion.

Acceptance corpus
-----------------------

``examples/manifest.json`` normatively specifies 27 acceptance/rejection cases and three
scripted scenarios. Valid examples are complete F0 files checked against the
selected net. Files under mutations are net-body fragments, not standalone nets.
The unsafe_paid_release net deliberately fails ordering despite balanced
accounting.

See :doc:`conformance` for required profiles, diagnostics and rule IDs.
The documentation validator checks valid examples against both the N0 API and
the N1 API projection. It also checks their lowerings. The prototype regression
suite adds coloured mutations and concrete crash scenarios. See the reproducible
commands in :doc:`tooling`.
