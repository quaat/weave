Reading a counterexample
==============================

These are actual diagnostics regenerated by this package. Diagnostic line numbers
refer to the named source, not this chapter. A trace witnesses one failure; it is
not an execution schedule every run must follow.

E320: balanced accounting, unsafe cancellation
----------------------------------------------------

The mutation changes the paid cancellation route to release stock. It remains
authorized and conserves counts, so parse/ownership validation and accounting
proof pass. The N0 ordering check rejects it:

.. literalinclude:: ../../validation/counterexample-E320.txt
   :language: text

.. list-table::
   :header-rows: 1

   * - Trace step
     - What changes
     - Why it matters
   * - reserve
     - available to held
     - The single order owns the stock obligation
   * - arm
     - held to escrow; registration created
     - Recovery is armed atomically
   * - dispatch
     - escrow to inflight; request created
     - Dispatch history becomes true
   * - charge_ok
     - inflight to paid
     - The classified guard establishes paid evidence
   * - cancel_paid (mutated)
     - paid and registration consumed; available produced
     - Stock is released after dispatch without rejected evidence

The named failing predicate is dispatched_release_requires_rejection:
available is marked, dispatch is true, and rejected_evidence is false.
The final marking also illustrates why conservation is insufficient: the count
is still one, but the business state is wrong. The leftover charge_requests
belongs to the legacy queue model and is not the reported violation.

E420: a read from the wrong order
---------------------------------------

This mutation reads registrations[t,other] during dispatch. Read arcs do not
change incidence coefficients, so aggregate and family accounting still pass.

.. literalinclude:: ../../validation/counterexample-E420.txt
   :language: text

.. list-table::
   :header-rows: 1

   * - Trace step
     - State established
   * - reserve order1
     - order1 has held and an active job
   * - reserve order2
     - order2 independently has held and an active job
   * - arm order1
     - order1 owns escrow and its registration exists
   * - arm order2
     - order2 owns escrow and its registration exists
   * - dispatch order1, other=order2
     - The enabled read uses order2's registration for an order1 firing

The last displayed mode is the rejected candidate, checked **before firing**;
it is not a committed bad successor. Both tokens exist, so ordinary enabledness
cannot detect the authorization error. The correlation property compares the
read cell's concrete colour with the primary firing colour and reports E420.

Mutation stages matter
----------------------------

Changing sell to consume another order's registration fails E412 in family
proof and E420 in a separate exploration. Simply deleting identities from
reserve while leaving its runtime consumer declaration intact fails E100 first.
Changing that declaration to terminal as well reaches the deeper E412 accounting
and E420 unique-admission checks. Report which mutation and which phase ran;
do not treat different first diagnostics as inconsistent analyses.
